# 组织文档维护

此仓库随 Desktop、Core、Browser 和 LMCP 的正式 `1.0.0` 更新组织入口；组织文档本身不打产品版本标签。四个软件仓的版本、产物和验证结果以所属仓库为准，组织首页不保存另一份接口规范。

## 提交前检查

```bash
npm ci --ignore-scripts
npm run verify
```

检查覆盖仓内 Markdown / 图片引用、公开资料路径、图源与正文以及两主题 SVG 摘要、格式。检查是纯文件读取，不启动浏览器，不访问云服务；生成图解仍按[图表规范](图表规范.md)维护。工作流在 main 推送、PR 和手动触发时运行，不部署网站或创建 Release。

修改 README 时核对各软件仓的功能与版本，不把测试用截图当作商店上线证明。尚未验证的平台、签名、公证和远端 Actions 应在对应发布记录中明确说明。

## 双平台维护

[GitHub](https://github.com/leximeet/.github) 与 [Gitee](https://gitee.com/leximeet/.github) 是平级的源码与协作入口，使用同一份 main 内容。组织仓库不打产品标签；软件仓在检查通过并确认发布后才创建 `1.0.0` 标签。版本字段不表示远端标签或发行物已经存在。

1. 修改前读取两个远端的 main，先处理尚未整合的提交，再进行同一份变更。
2. 任一平台接受的改动都进入同一条 main 历史，按授权将同一提交推送到两边。不要在两边各生成不同的“同版本”提交。
3. 只显式推送 main；完整开发历史、备份分支和 bundle 留作私有恢复，不使用 `git push --all` 或 `git push --tags`。
4. 分别核对两边远端的提交和发行状态。某个平台未完成时如实记录，不将另一边成功视作全部完成。

现有自动检查使用 GitHub Actions。Gitee 的代码托管不代表已配置同等流水线，维护者仍可从任一来源克隆后执行本页相同命令。站点部署、Release 与商店发布是独立动作，均需维护者明确授权。

## 已公开历史

首次公开整理保留原始 `init commit` 与当时的结果提交。之后正常追加提交，不为新增平台重复压缩已公开历史，也不覆盖任何远端已有提交。首次向另一平台推送前，核对其已有历史；发现差异应先审查和整合。

## 正式版本之后

正式 `1.0.0` 开始保护真实用户资料。后续数据结构变化需要迁移与升级测试；早期 `0.x/rc` 实验库不是受支持的正式格式，不能把拒绝旧测试库表述为丢弃正式用户资料。账号和设备云同步仍属于 `2.0.0` 路线。
